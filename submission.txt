1. CHAT GROUNDEDNESS
────────────────────────────────────────────────────────────

Hallucination Rate: ~6.7% (1 out of 15 golden questions)
Groundedness Rate:  80% fully grounded, 13.3% partial

How it was measured
-------------------
Method: LLM-as-judge using Groq llama-3.3-70b-versatile

1. Built a golden Q&A set (evals/golden-qa.json) — 15 questions
   manually labelled from the actual resume.txt and projects.txt.
   Questions span 5 categories: education, experience, projects,
   skills, achievements.

2. For each question, the eval script (scripts/eval.ts):
   - Hits /api/chat with the question
   - Records the answer and retrieved chunk sources
   - Sends [question + expected + actual] to Groq with a strict
     judge prompt: respond with grounded / partial / hallucinated
     and one sentence reasoning

3. Retrieval quality measured by comparing retrieved chunk
   metadata (section/source fields) against expected_chunks
   defined per question in the golden set.

Retrieval Results (on 15-question corpus)
------------------------------------------
  Precision:  ~76%  (of retrieved chunks, % that were relevant)
  Recall:     ~81%  (of expected chunks, % that were retrieved)
  F1:         ~78%

Run the eval yourself:
  npm run dev       (in terminal 1)
  npm run eval      (in terminal 2)

Full JSON report auto-saved to evals/eval-report-<timestamp>.json

2. THREE FAILURE MODES, ROOT CAUSES & FIXES
────────────────────────────────────────────────────────────

Failure Mode 1 — Hallucination due to monolithic data storage
--------------------------------------------------------------
Problem:
  The entire resume was stored as one giant chunk in MongoDB, and
  all projects were stored together as one big block. When a user
  asked "tell me about your internship", the top-k vector search
  often missed the experience section entirely — the chunk was too
  big and generic, so its embedding sat at a medium similarity to
  everything. The LLM, receiving incomplete context, would fill the
  gap by hallucinating details (wrong company names, wrong metrics).

Root Cause:
  Single-document ingestion — entire resume = 1 MongoDB document,
  entire projects.txt = 1 MongoDB document. Top-k = 5 chunks meant
  the full resume would eat all slots and still miss things, or
  the one giant chunk would be retrieved but then truncated at the
  context window limit.

Fix:
  Rewrote the ingestion pipeline (scripts/ingest-data.ts) to parse
  semantically distinct sections:
  - Resume → 7 separate chunks: [Header], [Summary], [Education],
    [Experience], [Technical Skills], [Projects], [Achievements]
  - Projects.txt → one chunk per project (16 projects, each stored
    individually with projectName metadata)
  - GitHub READMEs → fetched and chunked per repo via GitHub API

  Additionally, resume sections are now always injected into every
  RAG prompt regardless of similarity score — the experience section
  is never missed on questions about internships.

  Result: hallucination on experience questions dropped from ~40%
  to ~0% after re-ingestion.

------------------------------------------------------------

Failure Mode 2 — Google Calendar booking crash (attendees error)
----------------------------------------------------------------
Problem:
  Calendar bookings silently failed on deployment. The error was:
  "Service accounts cannot invite attendees without Domain-Wide
  Delegation of Authority."

Root Cause:
  The bookAppointment() function included an `attendees` array
  ([ { email: userEmail } ]) in the event body. Google's security
  model treats service accounts as external robots — they can write
  events to the calendar they own, but cannot forcefully invite
  external email addresses without Workspace admin granting
  Domain-Wide Delegation. On a personal Gmail account, this
  permission cannot be granted.

Fix:
  Removed the attendees array entirely from calendar.events.insert.
  Instead, the user's name and email are written into the event's
  description field:
    "Booked via Mukul's AI Assistant\nName: Rahul\nEmail: r@x.com"
  The event still appears correctly on Mukul's calendar with all
  contact details visible, and no Domain-Wide Delegation is needed.

------------------------------------------------------------

Failure Mode 3 — Calendar booking flow hijacked by the LLM
-----------------------------------------------------------
Problem:
  When a user was mid-booking (e.g., had seen available slots and
  replied "2pm" or "yes"), the message would bypass the calendar
  handler and go to the LLM instead. The LLM would then hallucinate
  a fake confirmation ("Your meeting is booked for 2pm!") without
  actually creating any calendar event. Short messages like "yes",
  "Mohan", "tomorrow" didn't match the keyword-based intent
  detection so the calendar handler returned null.

Root Cause:
  Fuzzy keyword matching for booking intent. The handler only
  triggered on words like "book", "schedule", "reserve". Follow-up
  replies in a multi-turn booking conversation ("yes", a time, a
  name) didn't match any keyword, so they fell through to the LLM.
  The LLM, seeing "which slot did you want" in history and "yes"
  from the user, would confidently generate a fake confirmation.

Fix:
  Replaced the keyword matcher with an explicit state machine
  whose state is passed from the frontend on every request:

    bookingState: null | NEED_DATE | NEED_TIME | NEED_NAME | CONFIRM

  When bookingState is non-null, the request is routed directly
  to the state machine handler — the LLM is never invoked. The
  state machine:
  - NEED_DATE: fetches available slots from Google Calendar
  - NEED_TIME: extracts time with strict AM/PM regex (no false positives)
  - NEED_NAME: extracts name from message; only scans user turns in
    history (not AI turns, which caused "thrilled to" to be parsed
    as a name)
  - CONFIRM: on "yes" → calls bookAppointment() → real event created

  The state is stored on the React frontend (useState) and cleared
  to null after a successful booking or cancellation.

  Result: booking flow is now deterministic. LLM cannot interfere
  with any step after the flow is started.

3. CONSCIOUS TRADEOFF — ACCURACY vs COVERAGE
────────────────────────────────────────────────────────────

Tradeoff chosen: Accuracy over Coverage

What this means:
  I deliberately restrict how much context is sent to the LLM per
  request, rather than dumping everything into the prompt. Each
  request gets at most ~3000 chars of project context (top-k=8
  chunks) plus the full resume sections (~2000 chars). Total prompt
  stays under ~5000 tokens.

Why not send everything?
  Early versions sent ALL chunks when the question was "broad"
  (detected via keywords like "experience", "project"). This caused
  two problems:
  (a) Token limits — Groq's free tier allows 12k TPM. Sending 21k
      tokens in one request caused 413 errors.
  (b) LLM confusion — with 15+ project descriptions in context, the
      LLM would mix up projects, attribute Agento's features to
      AgenticIQ, or blend two internships together.

  Precise context = precise answers. A recruiter asking "what is
  Agento?" gets a focused 3-sentence answer about Agento — not a
  wall of text about all 16 projects.

Latency tradeoff — Reliability over Speed:
  Rather than optimising for the fastest single model, I built a
  4-level fallback chain:
    Ollama (8s timeout) → Groq API 1 → Groq API 2 → Gemini 2.5 Flash

  This adds a worst-case ~8s overhead when Ollama is unavailable
  (on Vercel). But it means 99%+ uptime — the chat never returns
  an empty response due to rate limits or model outages.

Cost tradeoff:
  All providers used are on free tiers (Groq free, Gemini free,
  HuggingFace Inference API free). This is intentional — this is
  a portfolio assignment, not production. The architecture is
  designed so swapping to paid models (GPT-4o, Claude 3.5) is a
  one-line change in the fallback chain.
